VEX documentation

Guides and reference material for the VEX programming language.

WORKING DRAFT · 0.x
i

VEX is experimental. The compiler and language are actively evolving. This documentation describes verified behavior where available and labels unfinished areas instead of presenting plans as implemented features.

A first VEX program

VEX uses make to declare functions. A program can define main as its entry point and use say to write a supported primitive value to standard output.

hello.vex
make main() {
    let message = "Hello, VEX!"
    say(message)
}

Newlines separate statements. Curly braces delimit blocks; indentation is for readability and does not determine program structure.

Program structure

Functions and type declarations are defined at file scope. Function signatures are collected before function bodies are checked, so a function can call another function declared later in the same source file.

  • Use make name(...) to declare a function.
  • Use struct and enum for nominal user-defined types.
  • When make main() exists, it is the program entry point and top-level executable statements are rejected.
  • Without main, top-level statements execute in source order through a compiler-generated entry function.

VEX currently compiles a single source compilation unit. Module resolution and multi-file compilation are not yet implemented.

Types and bindings

VEX is statically typed. Local bindings can use inferred types when the compiler can determine the initializer's type. Function parameters require explicit type annotations.

bindings.vex
let count: int = 12
const gravity: float = 9.81
let enabled = true
let label = "simulation"

let introduces a mutable binding; const introduces an immutable binding. Mutable, explicitly typed scalar bindings may omit an initializer and receive defined defaults: zero for int and byte, 0.0 for float, false for bool, and the empty string for string. Inferred and constant bindings require initializers.

The current primitive set includes int, byte, float, bool, string, and void in their supported contexts. This is not a promise of fixed cross-platform integer width for every type.

Functions

Function parameters are explicitly typed. A function without a return annotation returns void; a function that returns a value declares its return type with ->.

functions.vex
make calculate_force(mass: float, acceleration: float) -> float {
    return mass * acceleration
}

Function overloading is not implemented. The compiler supports forward calls and recursive calls within the current compilation unit.

Structures

A struct declares a named value type with fields. Structure literals use named fields, and each declared field must be initialized exactly once.

structures.vex
struct Point {
    x: float,
    y: float,
}

make main() {
    let point = Point { x: 1.0, y: 2.0 }
    point.x = 4.0
    say(point.x)
}

Structures have value semantics: assignment, parameter passing, and return copy the structure value. Dynamic-array fields retain their shared reference when the containing structure is copied. Field layout follows the target ABI and may include padding; it is not a stable cross-platform serialization format.

Arrays of structures and nested field access are supported in the current implementation. Direct recursive by-value fields are rejected.

Enums and matching

Enums are nominal tagged unions. Each declaration defines a distinct type with a closed set of variants. Variants may carry zero or more positional payload values.

results.vex
enum SolverResult {
    Converged(int, float),
    Diverged(string),
    Cancelled
}

Variants are constructed with qualified names. The current match statement requires every declared variant to be handled exactly once. Enum values do not implicitly convert to integers.

Arrays and collections

VEX supports fixed-size arrays and dynamic arrays. Fixed arrays store elements by value; dynamic arrays use runtime-managed references to contiguous elements. Copies of a dynamic array share the referenced collection.

Current implementation includes indexing, iteration, nested dynamic and mixed fixed/dynamic jagged arrays, and collection operations. Nested aggregate storage is subject to target-aware limits. Borrowed slices and a complete ownership model are not available.

Control flow

The implemented control-flow constructs include if/else, while, counted repeat, for-in over arrays and integer ranges, and break/continue for the innermost enclosing loop.

Conditions require boolean values. Integer range iteration supports exclusive and inclusive forms. Labeled loop control, exceptions, async operations, and generators are not implemented.

Pointers and memory

The current pointer subset supports single-level typed pointers to mutable primitive, structure, and enum locals or parameters. Address-of, dereference reads and writes, compound stores, and projected field or array access are supported. Pointer parameters and directly returned borrowed pointers from a matching parameter are also supported.

!

This is not yet a complete systems-language memory model. Pointer-to-pointer types, null pointer values, pointer arithmetic, integer/pointer conversions, explicit unsafe boundaries, and complete lifetime, provenance, and aliasing rules remain unfinished. Returning a pointer to local storage is rejected.

Dynamic arrays and compiler-managed string allocations are released at normal generated-entry return. This is not per-scope deallocation, and the language does not yet expose a general allocator/deallocator API.

Standard library

The built-in API reference is being audited against semantic checking, lowering, both backends, runtime behavior, and tests. A function name alone is not a complete contract: each entry must document accepted argument types and shapes, arity, return values, side effects, failure cases, and backend guarantees.

Until that audit is complete, do not treat this page as an exhaustive standard-library signature list. Existing implementation notes are available in the source repository.

Errors and diagnostics

The compiler reports lexical, parsing, semantic, and intermediate-representation verification errors with source locations. Checked integer arithmetic and array indexing can fail at runtime rather than silently proceeding with invalid results.

A complete public catalogue of diagnostic codes, triggering conditions, and fixes is still being assembled. Recoverable error values and general exception handling are not implemented.

Compiler and backends

The initial compiler is implemented in C++20. Its pipeline includes source processing, semantic analysis, typed SSA intermediate representation, and backend code generation. The IR is designed to be backend-independent.

The project currently has C11 and LLVM code-generation backends. LLVM is the default native build path; C is retained as an optional bootstrap and fallback backend. Neither backend defines VEX language semantics.

Implementation status

VEX is an experimental language under active development. Some core language features are implemented and tested across both backends, while major areas of the language and runtime remain incomplete.

Implemented

Behavior exists in the compiler and is covered by tests.

Partial

Not implemented

A future capability or design area, not a current guarantee.
